## Assurance layer (added scope: the system proves its own safety)
Goal: make the system design technically impressive without adding features. Build in this order; each is backend-only and runs without live services (PGlite).
1. **Exhaustive policy verification** (DONE, `npm run verify:policy`; asserted in `lib/policy/exhaustive.test.ts`; 20,995,238 cases, 0 violations, ~11 s; 18 mutation tests prove the verifier fails on broken policies): enumerate the full input space of `decideOutcome()` and `nextState()`; prove `CONFIRMED_LEGIT` needs all four conditions and `released` is reachable only via a human `payment.released`. Print "checked N cases, 0 unsafe". This N backs the "0 unsafe releases" claim (PLAN s9) and replaces the older N definition.
2. **Deterministic simulation testing** (DONE: `npm run sim -- --seeds N [--start S] [--seed S]`, tests in `lib/sim/sim.test.ts`; 6,000 seeds = 11,949 calls, 93,296 deliveries, 25,350 forged requests, all invariants held; 5 mutation tests prove it fails on broken systems. **It found 2 real bugs:** (1) the reaper skipped calls whose `call_ended` arrived but `call_analyzed` was lost, stranding cases in `calling`; (2) `lpad(n,4,'0')` in the case-id default truncates, so case 10000 collided with an id (fixed with `next_case_id()` in `db/001`). Original spec: a seeded fuzzer replays the webhook pipeline (Retell + AgentMail) with duplicated, reordered, delayed and dropped events and bad signatures, then asserts invariants: one outcome per call, no release without a human, consistent log, held payments never un-held. A failing seed must reproduce exactly. Build after S9, since it hardens it.
3. **Hash-chained audit log** (~1.5 h): `db/003_*.sql` adds `prev_hash`/`hash` (trigger, advisory lock); `GET /api/audit/verify` recomputes the chain and reports the first break; UI shows a "chain intact" badge. Additive migration only.
4. **Event-sourcing replay check** (~1 h): replay the whole log through the pure reducer + `nextState()` and assert it reproduces every `cases.state`. Exposed by the same `/api/audit/verify`.
5. **Latency waterfall** (~1 h, UI): email -> flagged -> held -> call, from `llmMs`, `ramp.call.ms` and event timestamps.

## Backend invariants (never trade these for speed)
1. Fail closed. Any unclear state keeps payments held and creates a human task.
2. The LLM never releases money, never chooses a phone number, never sets a state. It reports; code decides. `decideOutcome()` (`lib/voice/decide.ts`) and `nextState()` (`lib/policy/lifecycle.ts`) are the only deciders. `canRelease()` plus the human release route are the only path to `payment.released`.
3. One writer: every event goes through `emit()` in `lib/store.ts`. Never `insert into events` elsewhere. `events` is append-only (DB triggers). Corrections are new rows.
4. The only number ever dialed is the primary `trusted_contacts` row for that vendor, and it must be in `ALLOWED_DEMO_NUMBERS`. Never read a phone number from an email, prompt, tool argument or request body.
5. Secrets stay server-side. Expected challenge digits live only in `cases.challenge_expected` and are read only by `CaseStore.getExpectedLast4`. Never in events, prompts, dynamic variables, metadata, logs or API responses. No `NEXT_PUBLIC_` vars unless listed in `.env.example`.
6. Every webhook verifies its signature on the RAW body first (`await req.text()`, never `req.json()` first), is idempotent, returns fast, and does work in `after()`. Bad signature: 401 (Retell, Ramp), 400 (Svix: AgentMail, Resend). Mutating human routes need the passcode session + same-origin `Origin` + `content-type: application/json`.
7. `request_summary` is built by `requestSummary()` in code, never from email text.
8. Never log full phone numbers, full bank numbers, API keys or challenge digits. `toRow()` redaction is the choke point. `toRow()` masks every E.164 number (length-preserving) and every digit run or spelled-out digit sequence in transcripts, `report_*` tool args and call summaries, because the events feed is public-read and the vendor SPEAKS the challenge answer. Decisions read the real digits from the database (`call_tool_calls`), never from events.
9. The UI derives everything from events via the pure `lib/reducer.ts`. Status comes only from `case.state` events. Money is never optimistic.
10. Ramp: `makeRamp()` picks mock (default, DB-backed) or sandbox. Hold at bill and vendor level; HTTP 202 means pending. The UI chip must say RAMP MOCK / RAMP SANDBOX truthfully; never claim "live in Ramp" in mock mode.
11. No SDK client and no `env()` call at module scope (`new Retell()`, `new Resend()`, `new Anthropic()`): `next build` imports every route module. Use a lazy getter.
12. Next 16 is not the Next you know: read the relevant page under `node_modules/next/dist/docs/` before route/config/caching code. Never enable `cacheComponents`; no `export const runtime`/`preferredRegion` in routes (`maxDuration` and `after()` are fine).
13. Post-call policy is `decideOutcome()` only. `postCallDecision()` in `lib/detect/policy.ts` exists for `eval/run.ts`; never import it from `app/` or `lib/`.
14. Public inbox + public repo: anyone can email the AP address. Calls stay behind `CALLS_ENABLED` and `INBOUND_ALLOWED_SENDERS`. `/api/demo/*`, `/demo`, `/dev/states` need the session and `DEMO_ENABLED=1` (else 404; `/dev/states` needs only `DEMO_ENABLED`).

## UI rules (`npm run lint:ui` must exit 0)
- **A first-time viewer must understand every screen in seconds, with no glossary.** Every case opens with a plain-language headline (`lib/copy.ts` `headline()`) and tells the same four-step story: email flagged -> payments put on hold -> vendor called on the number we already had -> result. No rule ids, no R1/R2 labels, no jargon in the UI. All user-facing wording lives in `lib/copy.ts`; when a signal or reason code is added, add its plain sentence there.
- Look: calm, soft, modern. Rounded corners from the token scale only (`rounded-sm/md/lg/xl`; arbitrary radii are linted), flat (no shadows, no gradients except the `--hatch` pattern and highlight sweeps), one hairline per surface, tone-on-tone cards (`components/ui/Card.tsx`). One accent (`--live`). Mono for ids, money and the stamp; everything else is sans, sentence case (`.cap` for quiet captions).
- Themes: `graphite` (neutral dark, default), `paper` (warm light), `cloud` (cool light), chosen with `?theme=` or the footer buttons, defined as CSS variable sets in `app/globals.css` under `[data-theme]`. Never write a hex value in a component; use semantic tokens (`bg-surface`, `bg-surface-raised`, `text-fg`, `text-fg-muted`, `border-rule`, `bg-live`, status colors via `Chip`).
- Tokens only, from `app/globals.css`. Never add a font, dependency, radius, shadow or gradient to fix a layout; fix layout, scale or copy, or delete.
- Fonts: Mona Sans (display and body), IBM Plex Mono (ids, money, stamp). Status chips are soft tinted pills with a glyph + text, never colour alone. Mapping from `case_state` is in `lib/copy.ts` `CHIP`.
- Stage 1280x720, no scroll for the main story beats. Less is more: one focal step open at a time, finished steps are a single line, the rest on demand.
- Motion: durations/easings from globals tokens, 8px max travel, no springs, a `prefers-reduced-motion` branch for each animation, a comment naming the state change it communicates.
- `components/**` (except `components/shadcn/`) are presentational: no `next/*`, no data fetching, no server code, so the Remotion project in `video/` can import them. Hooks for local UI state are fine.
- Icons: simple inline SVG or plain glyphs. No icon library, no emoji. Phones masked. Release is human-only, never optimistic. Render email text as text, never HTML.
